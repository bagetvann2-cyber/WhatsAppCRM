## 0. Коротко

Что добавляем:

1. **Выбор нейросети** для ИИ-помощника: Claude (уже есть), ChatGPT, Gemini.
2. **Свой ключ клиента (BYOK)**: у кого есть оплаченный ключ Claude/OpenAI/Gemini или
   другой нейросети, вставляет его, и бот отвечает за его счёт, а не за наш.
3. **Готовые анкеты**: заготовки под нишу (доставка, салон, клиника…). Выбрал, текст
   встал в поля, дальше правишь под себя.
4. **Генератор анкеты**: клиент своими словами описывает бизнес, ИИ собирает черновик
   анкеты и правил. Доступно только при активной подписке.

Главное архитектурное решение: **два адаптера, а не три и без новых npm-пакетов.**
Claude остаётся на уже установленном `@anthropic-ai/sdk`. ChatGPT, Gemini и «другие»
идут через один адаптер на обычном `fetch` по OpenAI-совместимому протоколу: у Gemini
есть официальный OpenAI-совместимый endpoint, у OpenRouter, DeepSeek, Groq, Mistral тоже.
Почему это важно для нас: воркер на проде живёт на вручную докатанных `node_modules`
(см. память по деплою). Любой новый пакет в цепочке `worker.ts → inbound-pipeline → ai-client`
уронит воркер с `MODULE_NOT_FOUND`. `fetch` встроен в Node, ставить ничего не нужно.

## 1. Как бот устроен сейчас

- `src/lib/ai-client.ts`: `askBot()` зовёт только Anthropic. Ключ один, `ANTHROPIC_API_KEY`
  из env. Два инструмента: `handoff_to_operator` и `save_order` (схема строится из полей
  заказа организации). Системная часть кэшируется (`cache_control`).
- `src/lib/ai-bot.ts`: список моделей `AI_MODELS` (только Claude), `COST_PER_ANSWER`
  (захардкожен в тенге, только Claude), `buildSystemPrompt`, `shouldBotReply`.
- `src/lib/ai-bot-store.ts`: `runAiBot()` берёт 12 последних сообщений, проверяет квоту,
  зовёт `askBot`, пишет `AiReply`, отправляет ответ в канал, пишет черновик заказа.
- Вызывается из воркера: `scripts/worker.ts → inbound-pipeline.ts → runAiBot`.
- Настройки: страница `/ai-bot`, форма `AiBotForm.tsx`, модель `AiBot` в Prisma
  (`model` строкой, `companyProfile`, `rules`, `answersLimit`, `answersUsed`).

### 2.2. Дыры в деньгах. С нашим ключом это критично, чинить в рамках задачи

1. **Клиент сам ставит себе размер пакета ответов.** `answersLimit` редактируется в форме
   `/ai-bot` любым владельцем. С нашим ключом это значит: поставил 1 000 000, и бот
   тратит наши $5 без ограничений. Лимит должен задавать тариф, а не клиент.
2. **Пакет «в месяц» сам не обнуляется.** В интерфейсе написано «в месяц», но
   `answersUsed` сбрасывается только кнопкой. Автоматического сброса по периоду нет.
3. **Бот не смотрит на подписку.** `isSubscriptionActive` проверяется только на `/billing`.
   Просроченный кабинет продолжает тратить наш ключ.
4. **Тест-чат без лимита.** `testBotAction` не списывает из пакета и ничем не ограничен.
   Кнопку «Спросить» можно жать бесконечно за наш счёт.
5. **Себестоимость захардкожена и только для Claude.** `COST_PER_ANSWER` в тенге по трём
   моделям. С тремя провайдерами нужна таблица цен за токены и расчёт по реальному
   расходу из `AiReply` (токены туда уже пишутся).
6. **По умолчанию стоит самая дорогая модель** (`claude-opus-5`, в `getBot` и в
   `saveBotAction`). На бюджете $5 по умолчанию должна быть дешёвая.

### 2.3. Качество ответов бота

7. **Вероятный баг: бот вызвал `save_order`, но не написал текст, и клиент остался без
   ответа.** `askBot` делает один запрос и не возвращает модели результат инструмента.
   Если модель ответила только вызовом `save_order`, то `answer = null`: заказ
   сохраняется, а сообщение клиенту не уходит. У OpenAI это обычное поведение (при
   tool call `content` часто пустой), у Claude бывает. Проверить по журналу `AiReply`
   (записи, где `answer IS NULL AND handoff = false AND error IS NULL`). Чинится вторым
   запросом с результатом инструмента, см. этап 1.
8. **Промт говорит «отвечаете клиентам в WhatsApp»**, а Telegram уже подключён.
   Мелочь, но на Telegram бот может написать «пишите нам в WhatsApp».
9. **Нет склейки быстрых сообщений.** Клиент пишет «привет» / «хочу заказать» / «пиццу»
   тремя сообщениями, получается три задачи в очереди и до трёх ответов подряд.
   В эту задачу не входит, записываю в долг (раздел 8).
10. **Проверка квоты не атомарная.** `shouldBotReply` читает `answersUsed`, инкремент идёт
    после ответа. Два параллельных воркера могут чуть превысить пакет. Сейчас воркер
    один и работает последовательно, так что это не срочно. Лечится, когда будет
    переделан учёт (этап 4).

### 2.4. Процесс и репозиторий

## 3. Решения по архитектуре

### Р1. Слой провайдеров: два адаптера

```
src/lib/llm/
  types.ts        — общие типы: LlmRequest, LlmResult, ToolDef, ProviderId
  catalog.ts      — провайдеры и модели: id, подпись, цены за 1M токенов, флаги
  anthropic.ts    — перенос текущего кода askBot (SDK, cache_control, effort)
  openai-compat.ts— fetch к /chat/completions: ChatGPT, Gemini, OpenRouter, DeepSeek
  errors.ts       — перевод ошибок провайдера в понятный текст
  index.ts        — complete(req, credentials): выбирает адаптер по провайдеру
```

- Инструменты описываются один раз в нейтральном виде `{ name, description, parameters }`
  (JSON Schema), каждый адаптер переводит их в свой формат (`input_schema` у Anthropic,
  `{type:"function", function:{…}}` у OpenAI).
- Ответ адаптера един: `{ text, toolCalls: [{name, input}], usage: {input, cached, output} }`.
- `askBot` остаётся точкой входа с той же сигнатурой плюс `provider`/`credentials`.
  `runAiBot`, тест-чат и тесты, которые мокают `@/lib/ai-client`, почти не меняются.
- **Второй проход (чинит баг из п.7):** если модель вызвала `save_order`, а текста нет и
  передачи оператору нет, отправляем ей результат инструмента («сохранено») и берём
  текст из второго ответа. Максимум 2 запроса на сообщение.
- Кэширование: у Anthropic остаётся явный `cache_control`. OpenAI и Gemini кэшируют
  длинный стабильный префикс сами. Системная часть уже идёт первой и не меняется, так
  что ничего делать не надо. Кэшированные токены у них лежат в
  `usage.prompt_tokens_details.cached_tokens`.
- Таймаут на запрос `AbortSignal.timeout(30_000)`. Ретраев в v1 нет: сбой пишется в
  `AiReply.error`, как сейчас.

### Р2. Наш ключ и ключ клиента живут по разным правилам

| | Наш ключ (платформа) | Свой ключ клиента |
|---|---|---|
| Кто платит провайдеру | мы | клиент |
| Модели | только проверенные из `catalog.ts`, дешёвые и средние | любые из каталога + свой id модели |
| Пакет ответов | задаёт тариф, клиент **не** редактирует, сброс раз в месяц | без нашего лимита (можно свой потолок) |
| Подписка неактивна | бот молчит | бот молчит (сервис платформы всё равно наш) |
| Тест-чат | лимит в сутки | без лимита |
| Ключ кончился / недействителен | — | бот молчит + плашка «ключ не работает» на `/ai-bot` |

**Тихого переключения на наш ключ нет.** Если ключ клиента умер, мы не начинаем
незаметно платить за него: бот молчит, владелец видит причину.

### Р3. «Другая нейросеть» = пресеты, а не произвольный URL

Если разрешить клиенту вписать любой адрес API, наш сервер пойдёт по этому адресу
(SSRF: можно постучаться во внутреннюю сеть сервера, в Postgres, в метаданные хостера).
Поэтому v1 даёт фиксированный список с зашитыми адресами:

- **Claude** (Anthropic), **ChatGPT** (OpenAI), **Gemini** (Google): наш ключ или свой.
- **OpenRouter**: только свой ключ. Один ключ даёт сотни моделей (Llama, Qwen, DeepSeek,
  Mistral, Grok…), так что «другая, которая нравится» покрывается почти полностью.
- (опционально) **DeepSeek** напрямую: только свой ключ.

Произвольный URL добавим, когда кто-то реально попросит, и тогда с проверкой: только
https, запрет приватных адресов.

### Р4. Хранение ключа клиента

- Шифруем существующим `src/lib/crypto.ts` (AES-256-GCM, тот же `ENCRYPTION_KEY`, что у
  токенов каналов). Поле `AiBot.apiKeyEncrypted`.
- В браузер ключ **не уходит никогда.** Показываем только `apiKeyHint` (последние 4
  символа) и дату проверки.
- При сохранении ключ проверяется бесплатным запросом (список моделей у провайдера).
  Неверный ключ не сохраняется.
- Ставить и удалять ключ может только владелец или админ (`canManageTeam`, как сейчас).
- Сырые тексты ошибок провайдера в журнал не пишем: 401 у OpenAI возвращает кусок
  ключа. `errors.ts` переводит статус в человеческий текст: 401/403 «ключ
  недействителен», 429 «лимит или деньги на счёте провайдера кончились», 5xx
  «провайдер временно недоступен».

### Р5. Название: «Готовые анкеты», а не «шаблоны»

Раздел «Шаблоны» (`/templates`) уже занят шаблонами сообщений WhatsApp для Meta. Два
разных «шаблона» в одном кабинете путают клиента. Новую фичу называем **«Готовые
анкеты»** и живёт она прямо на `/ai-bot`, над полем анкеты.

### Р6. Готовые анкеты: статичный файл, не таблица в БД

`src/lib/profile-presets.ts`: массив из 8–10 заготовок. Редактируем кодом. Таблица,
админка и CRUD не нужны, пока заготовки не начнут править не-разработчики.

Каждая заготовка содержит:
- `companyProfile` с местами для заполнения вида `[уточните: цена доставки]`;
- `rules` («чего не обещать») под нишу;
- `orderFields`: предлагаемые поля заказа (для доставки: имя, адрес, состав, время).
  Применяются галочкой и только если у организации полей заказа ещё нет. Чужие
  настроенные поля не затираем.

Ниши под Казахстан: доставка еды/кафе, интернет-магазин, салон красоты/барбершоп,
стоматология/клиника, автосервис, образовательный центр/курсы, недвижимость/аренда,
фитнес-клуб, цветы/подарки, бытовые услуги (ремонт/клининг).

**Защита от незаполненных мест:** при сохранении анкеты ищем оставшиеся `[уточните: …]`.
Если нашлись, сохраняем, но бота не включаем и показываем список незаполненного. Иначе
бот честно ответит клиенту «доставка стоит [уточните: цена доставки]».

### Р7. Генератор анкеты

- Кнопка «Собрать анкету с ИИ» открывает поле «Опишите бизнес своими словами: что
  продаёте, цены, адрес, часы, доставка, оплата».
- Серверный экшен зовёт **наш** ключ, одну фиксированную модель из замера этапа 0 (через уже установленный SDK: принудительный вызов инструмента
  `fill_profile` → `{companyProfile, rules, orderFields}`). Структурированный вывод
  надёжнее, чем просить JSON текстом.
- Метапромт: использовать только факты из описания, недостающее помечать
  `[уточните: …]`, цены и сроки не выдумывать. Та же логика, что у самого бота.
- Результат **не сохраняется сам**, он заполняет поля формы. Клиент правит и жмёт
  «Сохранить».
- Доступ: только при активной подписке (`isSubscriptionActive`), только владелец/админ,
  лимит N генераций в сутки на организацию.
- Каждый запуск пишется в журнал (`AiGeneration`), нужен и для лимита, и для учёта расхода.

## 4. Изменения в базе (одна миграция)

```prisma
enum AiProvider {
  ANTHROPIC
  OPENAI
  GEMINI
  OPENROUTER
}

model AiBot {
  // …существующие поля…
  provider         AiProvider @default(ANTHROPIC)
  model            String     @default("<модель из замера этапа 0>")  // было claude-opus-5
  /// Свой ключ клиента, зашифрован (src/lib/crypto.ts). null — отвечаем нашим ключом.
  apiKeyEncrypted  String?
  /// Последние 4 символа — чтобы клиент узнал свой ключ, не видя его целиком.
  apiKeyHint       String?
  apiKeyCheckedAt  DateTime?
  /// Последняя ошибка ключа клиента, понятным текстом — для плашки на /ai-bot.
  apiKeyError      String?
  /// Начало текущего периода пакета: сброс answersUsed раз в месяц.
  answersPeriodStart DateTime @default(now())
}

model AiReply {
  // …существующие поля…
  provider   AiProvider?
  model      String?
  ownKey     Boolean @default(false)
}

model Plan {
  // …существующие поля…
  /// Ответов ИИ в месяц на нашем ключе. Клиент со своим ключом этим не ограничен.
  aiAnswersPerMonth Int @default(100)
}

model AiGeneration {
  id             String   @id @default(cuid())
  organizationId String
  organization   Organization @relation(fields: [organizationId], references: [id], onDelete: Cascade)
  inputTokens    Int @default(0)
  outputTokens   Int @default(0)
  error          String?
  createdAt      DateTime @default(now())
  @@index([organizationId, createdAt])
}
```

Существующие строки `AiBot` получат `provider = ANTHROPIC`, а их `model` не меняется:
у кого стоит Opus, тот на нём и останется. Дефолт меняется только для новых.

Незакоммиченная миграция из работы по почте должна лечь **раньше** этой, см. этап 0.

- второй проход срабатывает только когда нужно и не больше одного раза;
- ошибки 401/429/500/таймаут переводятся в понятный текст, ключ в текст не попадает;
- старые тесты `ai-bot.test.ts` зелёные без правок логики.

**Готово, когда:** тест-чат на `/ai-bot` отвечает через все три провайдера на наших
ключах (живьём, после пополнения по $5).

### Этап 2. Схема, ключ клиента, проверка ключа

`src/lib/llm/verify-key.ts`, `src/app/(app)/ai-bot/actions.ts`.
- Миграция из раздела 4.
- `saveApiKeyAction` / `removeApiKeyAction`: проверка ключа бесплатным запросом →
  шифрование → `apiKeyHint`. Ключ из ответа экшена не возвращается.

  пишет `apiKeyError` (для плашки) и не падает.

Тесты: ключ хранится зашифрованным и не читается в открытом виде из `getBot`;

## 6. Риски

| Риск | Что делаем |
|---|---|
| У OpenAI/Gemini чаще бывает «вызвал инструмент, текста нет» | второй проход (этап 1) + живой тест заказа на каждом провайдере |
| OpenAI-совместимый режим Gemini отстаёт от родного API по фичам | для нас нужны только текст + инструменты; проверяем на этапе 0; при проблеме пишем родной адаптер Gemini на `fetch` (≈150 строк) |
| Модели выходят и снимаются каждые пару месяцев | модели в `catalog.ts` и в БД строкой; на своём ключе можно вписать id вручную |
| Разные модели по-разному держат «не выдумывай цены» | тот же системный промт у всех + живой тест вопроса вне анкеты на каждом провайдере |
| $5 на провайдера кончатся на тестах | дефолт на дешёвые модели, лимит тест-чата, реальный расход видно в журнале по токенам |
| Утечка ключа клиента | шифрование, ключ не уходит в браузер, ошибки провайдера без сырого текста |

## 7. Что сознательно не делаем в этой задаче

- Произвольный URL API (SSRF, см. Р3). Добавим по запросу, с проверкой адреса.
- Автопереключение на другую нейросеть при сбое. Непредсказуемо по деньгам.
- Списание ответов ИИ с баланса в тенге по реальным токенам. Пакет по тарифу проще
  и понятнее клиенту; расчёт по токенам можно добавить позже, данные уже пишутся.
- Таблица заготовок в БД и админка для них.
- Склейка быстрых сообщений клиента (п.9): полезно, но это отдельная задача про
  очередь, а не про нейросети.

## 8. Долг, записанный по ходу анализа (вне этой задачи)

## 9. Поправки после CEO-ревью (2026-09-19)

Проверено живыми запросами к API ключом проекта:
- `claude-haiku-4-5` + `output_config.effort` → `400 This model does not support the effort parameter`.
  Без effort Haiku работает. Sonnet 5 работает и с effort, и без.
- Принудительный вызов инструмента (`tool_choice` на конкретный инструмент) работает на Sonnet 5
  (с effort и без) и на Haiku 4.5.

П1. **Баг в проде уже сейчас.** `askBot` всегда шлёт `effort: "low"`, а Haiku 4.5 его не
поддерживает. Кто выберет Haiku на `/ai-bot`, у того бот падает на каждом сообщении: ошибка
пишется в `AiReply.error`, клиенту тишина. Чиним первым отдельным коммитом этапа 1: в
`catalog.ts` у каждой модели флаг `supportsEffort`, адаптер не шлёт effort моделям без него.
Тест: для модели без флага запрос уходит без `output_config.effort`.

П2. **Модель по умолчанию выбирается замером, а не по прайсу.** Этап 0: 15–20 типовых диалогов
(русский и казахский, вопрос вне анкеты, заказ из нескольких сообщений) на кандидатах каждого
провайдера. Считаем стоимость ответа по реальным токенам с учётом порога кэширования модели
(анкета в ~2000 токенов может не дотянуть до минимального кэшируемого префикса), долю
правильных передач оператору и долю верных `save_order`. Результат — таблица в плане; дефолт в
`catalog.ts` и в схеме берётся из неё. Везде выше, где сказано «Haiku 4.5» или «дешёвая модель
по умолчанию», читать «модель из замера».

П3. **Бот не молчит молча.** Если бот включён, но ответить не может (пакет кончился, подписка
неактивна, ключ клиента не работает, модель вернула передачу оператору без текста, провайдер
упал или не ответил), клиенту уходит фраза-заглушка без обращения к модели. Текст настраивается
на `/ai-bot`, по умолчанию «Передал ваш вопрос менеджеру, ответим в рабочее время». Заглушка
считается передачей оператору: ставим `handedOffAt`, поэтому повторно она не уйдёт, пока диалог
у человека. Причина пишется в `AiReply`. Закрытое окно WhatsApp по-прежнему означает тишину
(отправить нельзя). Тесты: по одному на каждую причину, плюс «вторая заглушка в тот же диалог
не уходит».

П4. **Пакет по тарифу рассчитывается, а не ставится 100.** `aiAnswersPerMonth` для каждого тарифа
считается из цели «себестоимость ИИ не больше 10–15% цены тарифа» по цене модели из замера (П2).
У пробного периода отдельный небольшой пакет. Сброс пакета: при оплате периода подписки
(`markInvoicePaid` → `answersUsed = 0`, `answersPeriodStart = now`) и лениво раз в месяц внутри
оплаченных 6/12 месяцев. При 80% израсходованного — плашка на `/ai-bot` и `/inbox`.
Списание атомарное и до запроса: `updateMany where answersUsed < limit` резервирует ответ;
если провайдер упал с ошибкой, резерв возвращается. Тесты: сброс при оплате, ленивый сброс,
плашка на 80%, возврат резерва при сбое провайдера.

П5. **Свой id модели сохраняется только после пробного вызова инструмента.** При сохранении один
запрос с тестовым инструментом; если модель не вернула вызов — отказ: «Эта модель не умеет
передавать диалог оператору — выберите другую». Иначе бот без `handoff_to_operator` и
`save_order` будет сам отвечать про цены, которых нет в анкете.

П6. **DeepSeek напрямую убран из v1.** На `/ai-bot` рядом с выбором провайдера подпись
«Переписка с клиентами передаётся выбранному провайдеру ИИ». Список провайдеров добавить в
оферту и политику конфиденциальности, когда они появятся на лендинге.

П7. **Метрики успеха** (из `AiReply` и `Order`, без новых таблиц): время от регистрации до первого
ответа бота, доля ответов с передачей оператору, число заказов, собранных ботом. Карточка на `/reports`.

П8. **Генератор оставляет принудительный вызов инструмента.** Проверено запросом, работает на
обоих кандидатах. Структурированный вывод не нужен.

П9. **Порядок этапов: 0 → 1 → 4 → 5 → 6 → 2 → 3 → 7.** Защита денег (4) идёт раньше, чем на наших
ключах появятся новые модели. Онбординг (5–6) идёт раньше своего ключа клиента (2–3). Свой ключ
клиента остаётся в объёме задачи.

П10. **Тест-чат с историей.** Проверка на нескольких репликах подряд, а не на одном вопросе.
История живёт в форме и в базу не пишется. В журнале «Что отвечал помощник» у каждого ответа
показана его стоимость по таблице цен каталога.

П11. **Ключ клиента привязан к провайдеру.** Ключ хранится вместе с провайдером (`apiKeyProvider`).
При смене провайдера сохранённый ключ удаляется. Интерфейс заранее предупреждает об этом и просит
ввести ключ нового провайдера или перейти на наш ключ. Ключ OpenAI никогда не уходит в Gemini.

П12. **Ошибки, которых не было в плане.**
- Ключ клиента не расшифровался (сменился `ENCRYPTION_KEY`): `apiKeyError` = «Ключ нужно ввести
  заново» + заглушка из П3.
- Провайдер снял модель (404 `model_not_found`): плашка «Модель больше недоступна у провайдера —
  выберите другую» + заглушка.
- Пустой ответ без вызовов инструментов и отказ модели (refusal / content_filter) обрабатываются
  как «нет ответа»: заглушка + причина в журнале.

П13. **Шифрованный ключ не уходит в браузер даже в зашифрованном виде.** `getBot` для страницы
возвращает только `apiKeyHint`, `apiKeyProvider`, `apiKeyCheckedAt`, `apiKeyError`; сам
`apiKeyEncrypted` читается только в серверном коде бота. Тест: пропсы `AiBotForm` не содержат
`apiKeyEncrypted`.

П14. **Провайдер без нашего ключа на сервере** (например, не задан `GEMINI_API_KEY`) в варианте
«наш ключ» показан недоступным, со своим ключом — доступен.

П15. **Медленный провайдер одной компании не должен задерживать ответы других.** Воркер сейчас
обрабатывает очередь по одному сообщению, и 30-секундный таймаут одного медленного провайдера
(свой ключ, OpenRouter) останавливает всех. Требование: параллельная обработка разных диалогов
при последовательной обработке сообщений одного диалога. Механизм выбирает eng-ревью (pg-boss).

П16. **Наблюдаемость.** Каждый вызов модели пишет одну строку в лог воркера: провайдер, модель,
время ответа в мс, токены, исход. В `AiReply` добавляется `latencyMs`. Скрипт `npm run ai-spend`
считает расход наших ключей по провайдерам за период (токены × цены каталога, только
`ownKey = false`). Так видно, сколько осталось от $5 на каждом провайдере.

Отложено (в раздел 8 и в TODOS.md): казахские версии готовых анкет; живое демо на лендинге
«бот по описанию бизнеса» с лимитом по IP.

- `saveApiKeyAction` одним действием сохраняет ключ, провайдера и модель по умолчанию для него.
- OpenRouter работает только со своим ключом.
- Провайдеры — `fieldset` + `legend` + `input type="radio"`, на телефоне сетка 2×2. Недоступный
  провайдер неактивен и называет причину. У OpenRouter метка «Только со своим ключом». Под группой —
  подпись о передаче переписки (П6). У каждого провайдера ссылка «Где взять ключ →».

Д6. **На нашем ключе модель одна на провайдера** (победитель замера), выбора нет. Сервер отклоняет
модель не из списка разрешённых. Выбор модели и `<datalist>` — только на своём ключе. Существующие
строки на нашем ключе миграция переводит на модель по умолчанию (платящих клиентов пока нет). Это
заменяет фразу раздела 4 «у кого стоит Opus, тот на нём и останется».

Д7. **Деньги в интерфейсе.**
- Наш ключ: только «Осталось N из M, обновится ДД.ММ». Себестоимость в тенге клиенту не показываем.
- Свой ключ: «≈ $0,002 за ответ · списывается с вашего счёта у провайдера».
- Это отменяет для нашего ключа «стоимость каждого ответа в журнале» из П10.
- Своего потолка на своём ключе нет: лимит задаётся у провайдера, даём ссылку. Это отменяет «можно
  свой потолок» в таблице Р2.

Д8. **Проверка ключа — три исхода.**

| Ответ провайдера | Текст | Ключ |
|---|---|---|
| 401/403 | «Ключ недействителен» | не сохраняем |
| 429 или `insufficient_quota` | «Пополните баланс у провайдера →» | не сохраняем |
| 5xx или таймаут | «Провайдер не отвечает, попробуйте позже» | не сохраняем, неверным не называем |

- Во время проверки «Проверяем ключ…», кнопка неактивна.
- Поле ключа: `type="text"`, `autocomplete="off"`, `spellCheck={false}`, после сохранения очищается.
- `apiKeyError` снимается при первом успешном вызове. На плашке кнопка «Проверить снова». Разовый 429
  по частоте запросов ошибкой ключа не считается.

Д9. **Незаполненные места `[уточните: …]`** (в анкете и в правилах).

## 11. Поправки после DX-ревью (2026-09-19)

Х1. **Сведение плана перед кодом.** До первой строки кода разделы 9–11 переносятся в разделы 3–5,
устаревший текст удаляется, схема БД остаётся одним блоком. Тело плана становится единственным
источником правды.

Х2. **Этапы и миграции, которые реально выполнить по порядку.**
- Этап 1 выпускает скрипт `npm run ai-bench -- --provider gemini --model X [--dialogs file]` поверх
  `complete()`.
  - Это проверка готовности этапа 1: ответ на всех трёх провайдерах через `ai-bench`, а не через
    тест-чат.
  - Этот же скрипт делает замер из П2. Замер переезжает из этапа 0 в конец этапа 1.
- Миграции разбиты по этапам:

  | Этап | Что добавляет миграция |
  |---|---|
  | 1 | `provider`, `model` (nullable) |
  | 4 | поля тарифа и периода |
  | 6 | `AiUsage` |
  | 2 | поля ключа |

Х3. **У каждой ошибки есть хозяин.** `errors.ts` возвращает `{ code, owner: "client" | "platform" }`.
- Ошибка наша (например, на нашем ключе OpenAI кончились $5 — `insufficient_quota`): клиент в
  баннере видит «Помощник временно не отвечает, мы уже разбираемся», воркер пишет `console.error`
  с тегом `llm_platform_error`.
- В `apiKeyError` попадают только ошибки клиента.

Х4. **Проверка ключа — один пробный вызов модели, которая сохраняется**, с принудительным вызовом
инструмента. Этот вызов заменяет и запрос списка моделей, и отдельную проверку из П5.
- Коды разбираем по полю ошибки провайдера:

  | Провайдер | Код | Что значит |
  |---|---|---|
  | OpenAI | `insufficient_quota` | кончились деньги |
  | OpenAI | `rate_limit_exceeded` | лимит частоты |
  | OpenRouter | 402 | нет кредитов |
  | Gemini | 400 `API_KEY_INVALID` | неверный ключ |
  | Gemini | `RESOURCE_EXHAUSTED` | лимит частоты |
  | любой | прочий 4xx | «Провайдер отклонил ключ: <код>» |

- Уточнение к Д8: 429 без `insufficient_quota` — «Лимит частоты, попробуйте через минуту», а не
  «Пополните баланс».
- Что отвечает OpenAI-совместимый endpoint Gemini, проверяем через `ai-bench` на этапе 1.
- Под кнопкой: «Проверка — один короткий запрос, меньше цента с вашего счёта».

Х5. **Одна таблица исходов `BotOutcome`** в `ai-bot.ts`: `{ label, banner, action, owner, sendsStub }`.
- `AiReply` хранит код исхода.
- Баннер, журнал и заглушка читают эту же таблицу.
- `REASON_LABEL` входит в неё.

Х6. **Для отладки.** `AiReply` хранит код исхода, HTTP-статус и поле `code`/`type` ошибки провайдера,

На вырезание есть тест.

Х7. **`LlmRequest.toolChoice?: "auto" | "required" | { name }`.** Генератор и пробный вызов идут через
`complete()`, прямой вызов SDK из Р7 отменён. Поэтому лог, ошибки и цены у всех вызовов одинаковые.

## 12. Поправки после инженерного ревью (2026-09-19)

Проверено по коду:
- `handedOffAt` пишется только в `ai-bot-store.ts:167` и нигде не сбрасывается.
- Вход отклоняется при `emailVerifiedAt = null` (`src/app/(auth)/actions.ts`). Миграции под новые поля нет, а `acceptInvite` (`src/lib/team.ts`) создаёт пользователя без `emailVerifiedAt`.
- SDK Anthropic по умолчанию ждёт ответа 10 минут и делает 2 повтора.
- pg-boss 12.33 поддерживает `group` и `localGroupConcurrency`.

И1. **Заглушка не ставит `handedOffAt`.**
- Повтор заглушки гасится по последнему `AiReply` с исходом «заглушка» в этом диалоге за 6 часов.
- `handedOffAt` ставит только передача оператору, которую вызвала сама модель.
- Тест: причину устранили — бот снова отвечает в том же диалоге.
- Это исправляет П3: иначе один сбой провайдера ночью навсегда отключал бы бота для этого клиента.

И2. **Этап 0: работа по почте до мержа PR #1.**
- Миграция: `UPDATE "User" SET "emailVerifiedAt" = "createdAt"` для всех существующих пользователей.
- `acceptInvite` ставит `emailVerifiedAt: new Date()`: почту подтверждает сама ссылка приглашения.
- Тесты: входит существующий пользователь, входит приглашённый сотрудник.
- Без этого после выката не смогут войти все, включая владельца.

И3. **Ошибка платформы доходит до нас.** Если наш ключ кончился или отклонён, приходит письмо на
`PLATFORM_ALERT_EMAIL` через существующий Resend (`src/lib/email.ts`). Не чаще раза в час на пару
«провайдер + код», счётчик держим в памяти воркера. В кабинетах провайдеров руками включить уведомления
о расходе.

И4. **Таймауты и повторы** — первым коммитом этапа 1, вместе с П1.
- Клиент Anthropic: явный `timeout`, `maxRetries: 0`.
- Одна политика повторов в обоих адаптерах: один повтор на 429, 5xx и обрыв соединения, `retry-after` не
  дольше 5 с.
- Общий дедлайн на обработку одного сообщения — 45 с, включая второй проход.

И5. **Механизм П15.**
- `boss.send(Q, job, { singletonKey: job.messageId, group: { id: job.conversationId } })`.
- `boss.work(Q, { localConcurrency: 5, localGroupConcurrency: 1 }, handler)`.
- Политика очереди `standard` не меняется.
- Параллельность включается только после атомарного резерва (этап 4) и держится ниже размера пула pg.
- Тест: два задания одного диалога не идут одновременно, задания разных диалогов идут параллельно.

И6. **Второй проход живёт внутри адаптера** и возвращает модели её исходное сообщение без изменений:
- Anthropic: блоки `thinking` остаются нетронутыми, `tools` передаются в запросе.
- Gemini через OpenAI-совместимый endpoint: `extra_content` в `tool_calls` сохраняется.
- Все провайдеры: на каждый `tool_call id` свой ответ инструмента.

Во втором запросе `tool_choice: "none"`, токены обоих запросов суммируются. Тесты на все три ситуации.

И7. **Ограничения входа на сервере.**
- Анкета вместе с правилами — до 8000 символов, и при сохранении, и в тест-чате.
- Каждое сообщение истории обрезается до 1500 символов.
- История тест-чата — до 12 реплик.
- Описание для генератора — до 2000 символов.

И8. **До начала пробного периода** (`trialEndsAt = null`) тест-чат и генератор на нашем ключе работают в
пожизненном лимите по `AiUsage`: 30 проверок и 5 генераций всего. После начала периода — суточные лимиты.

И9. **`usage` в одной форме.**
- `input` — все входные токены, `cached` — их часть из кэша, `cacheWrite` отдельно (у Anthropic это
